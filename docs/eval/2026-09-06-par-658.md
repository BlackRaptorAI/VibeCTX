# PAR-658 retrieval evaluation — legacy overlap ranker vs BM25

**Date:** 2026-09-06 · **Branch:** `build/par-658-bm25` · **Decision:** D-27

## Verdict, first

**BM25 did not beat the legacy ranker on this probe set. Both score 18/60 top-1
hits (18/23 of the answerable questions). MEASURED, not asserted.** The two
rankers disagree on the top result for 12 of the 60 questions, but every one of
those 12 is a question this corpus cannot answer, so BM25 gained 0 hits and lost
0. PAR-658's "correct section in top result improves over the current ranker"
done-when is **NOT met on this corpus**; see *What this does and does not show*.

## How the numbers were produced

- Script: `scripts/eval-retrieval.mjs`, run as `npm run build && node scripts/eval-retrieval.mjs`.
- Gold: `docs/eval/probe-gold.json` — 60 questions, being each of the 30 registry
  entries paired with each of its two `probeQueries`. Each question carries
  heading-path regexes for the section that would count as the correct top result,
  labelled by reading the fetched documents **before** either ranker was run over
  them, under the labelling rule stated in that file's header.
- Legacy baseline: the `tokenize` / `splitSections` / `rankSections` / `assemble`
  from `src/retrieval.ts` at 5b31f33, copied verbatim into the script so the
  baseline cannot drift with `src/`.
- Both rankers rank the **primary document only** — index links are not followed,
  so the two are compared on identical input.
- Response size is the rendered `assemble(ranked, 4000)` length divided by 4
  (VibeCTX's own approximate-token unit).

## Corpus provenance — read this before trusting the hit rates

Every one of the 30 documents in this run was the entry's
**`raw.githubusercontent.com` README fallback**. Not one docs-site
`llms-full.txt` / `llms.txt` primary was reachable from the build sandbox, which
has network access to `registry.npmjs.org`, `pypi.org` and
`raw.githubusercontent.com` only. The per-question table below records the
resolved URL class; the script prints each URL to stderr.

That matters enormously. A README is a fraction of an `llms-full.txt`: **37 of
the 60 probe queries have no correct answer anywhere in the document that was
fetched** (`expect: []` in the gold file, with a per-question reason). Prisma's
README never says "upsert"; the Stripe library README never says "checkout";
Tailwind's README is four sections of links. The probe queries were written
against the real docs sites, and the real docs sites are exactly what this
sandbox cannot see.

So these hit rates measure the two rankers **against a corpus neither was
designed for**. They are a valid A/B — same input, same gold — and an invalid
estimate of production quality in either direction.

## What this does and does not show

**Even.** Neither ranker wins a single question the other loses. On the 23
answerable questions both pick the same section 18 times, and both miss the same
five: `ai-sdk / streamText tool calling`, `zod / parse object schema`,
`bun / Bun.serve http server`, `playwright / locator click`,
`astro / islands client directive`.

**BM25 answers more often (12 → 8 "no sections matched").** The new tokenizer's
camelCase splitting is what does it: `useUser hook` tokenizes to
`use, user, useuser, hook`, and `use` occurs in almost any document, so clerk's
README now returns a section where the legacy ranker correctly returned nothing.
Recall up, precision unchanged **on this corpus** — and on a README the extra
recall is noise. On an `llms-full.txt`, where the answer usually does exist, the
same behaviour is the point of the change; that is a hypothesis this run cannot test.

**Responses got 11% longer (861 → 960 tokens).** Same cause: BM25 admits more
sections above zero, and `assemble` fills the 4,000-token budget with them.

**One concrete stemmer defect, MEASURED.** `tokenize("parse")` → `["parse"]` but
`tokenize("parsing")` → `["pars"]`: D-23's two-pass suffix stemmer removes `ing`
without restoring the silent `e`, so the two do not converge. That is exactly why
`zod / parse object schema` misses the "Basic usage > Parsing data" section. The
rule is D-23 as written and was not changed here; it is filed as a follow-up.

**`mode: "snippets"` has something to return on 35 of the 60 questions** — that is
a capability count on this corpus, not a quality measurement. No gold set exists
for snippets yet.

| `getDocs(prisma, "upsert", mode: "snippets")` | source `raw.githubusercontent.com/prisma/prisma/main/README.md`; **0 snippets matched** → `No code snippets matched "upsert" in prisma docs (source: …). Try mode "sections" or broader terms.` |

Neither returns the call PAR-658 names, because neither call is in the README the
sandbox can reach: `stripe.checkout.sessions.create` lives in
`docs.stripe.com/llms-full.txt` and `prisma.user.upsert` in
`prisma.io/docs/llms-full.txt`, both unreachable here. **The done-when
"`mode: "snippets"` returns runnable code for 'stripe checkout session create'
and 'prisma upsert'" is NOT VERIFIED against the real docs sites.** The mechanism
is proven instead by unit tests over fixture markdown shaped like those pages —
`test/retrieval.test.ts` "returns the Stripe checkout-session call for 'stripe
checkout session create'" and "returns the Prisma upsert call for 'prisma
upsert'", plus `test/get-docs.test.ts` "returns the fenced code block with its
heading path and context line, and the Source line".

## Reproducing

```
npm run build
node scripts/eval-retrieval.mjs
```

The script caches fetched documents under `$TMPDIR/vibectx-eval-cache` (override
with `DOCS_CACHE_DIR`), so a second run is offline and byte-identical. Run it
from a machine with unrestricted network access to get the numbers that matter:
the same 60 questions against the `llms-full.txt` primaries. Those numbers do not
exist yet and are not claimed here.

## Standards applied

No published standard governs retrieval evaluation for this use. The practice
applied is a fixed, pre-labelled top-1 relevance set with a frozen baseline
implementation, scored by exact A/B on identical input — the gold set was written
from the documents before either ranker was run and was not adjusted afterward.
