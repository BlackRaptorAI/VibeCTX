against a 300 ms bound — while measuring **16.1 ms in isolation**, an 18× margin. The bound is not

> no terminating condition, and each round produces an honest-looking fix that makes the test weaker.
> **Diagnose the root cause first.** A10's real fix was scaling both corpora 4×, found by diagnosis,

## Target 1 — `test/search-perf.test.ts:153` (the confirmed flake)

```js
const D37_BUDGET_MS = 300;                       // :49
…
expect(warm.fromIndex).toBe(LIBRARY_COUNT);      // :138
expect(warm.tokenized).toBe(0);                  // :139
…
console.log(`[D-37 MEASURED] corpus … warm search ${warmMs.toFixed(1)} ms …`);   // :147-152
expect(warmMs).toBeLessThan(D37_BUDGET_MS);      // :153   <-- the flake
```

**Read D-37 before deciding anything here. It is the decision this assertion claims to serve:**

> **D-37** — *"Search performance is **measured, not asserted**: a test proves warm search over ≥10
> indexed documents / ≥5 MB **and reports the time** (44 ms), a second proves the index is actually
> used (1 tokenize call with it, >2,640 without)…"*

**D-37 requires the time to be REPORTED. It does not require a threshold.** The `[D-37 MEASURED]`
print at `:147` already satisfies it. And the deterministic property D-37 names — *"the index is
actually used"* — is **already asserted, deterministically, two lines above**, at `:138` and `:139`.

**So the leading candidate is: delete `:153`, keep the print.** That is not a weakening of D-37 — it
is a return to what D-37 says, and it is done-when rule 2's first option, "gates on determinism". It
also matches `CONTRIBUTING.md:77`: *"the number is the record, the threshold is not."*

**You are not ordered to take that route.** Diagnose first and justify what you do. If you conclude
the threshold earns its keep, keep it — but then you owe a bound with **measured margin at a stated
load level**, and the measurement, not the assertion, is the deliverable. **If you delete it, say
plainly in the commit message that a performance guard was removed and what now protects the
property**, so nobody later reads the deletion as a silent weakening.

## Target 2 — `test/server.test.ts:192` (unmeasured, and PAR-733's line number is wrong)

**PAR-733 cites `:169`. That is stale — `:169` is now a schema assertion.** The real code is `:192`:

```js
const list = await Promise.race([call("list_libraries"), new Promise<string>((_, rej) => setTimeout(() => rej(new Error("list_libraries blocked")), 1000))]);
```

**Three things to understand before touching it.**

1. **It is not an assertion.** It is a rejection timer. It has no `expect`, so it appears in no
   `toBeLessThan` sweep — which is exactly why both earlier inventories missed it. It fails by
   throwing, not by asserting.
2. **It is a LIVENESS test, not a performance test.** The surrounding test holds autowarm's fetch
   open deliberately (`heldFetch()`) and asserts `list_libraries` still answers and marks zod
   `warming…`. The property is *"does not block behind the held fetch"* — i.e. does not hang. 1000 ms
   is a stand-in for "forever".
3. **It has never been exercised under load by anyone.** This is **unmeasured risk, not a confirmed
   flake**, and must not be described as one.

**Done-when rule 2's third option is written for exactly this shape:** *"an explicit per-test timeout
that lets it fail cleanly at its own boundary rather than dying inside vitest's implicit 5000 ms
default."* Whatever you do, the test must (a) still distinguish *blocked* from *slow*, (b) carry a
`[MEASURED]` print of the real elapsed time, and (c) fail with a message that says which it was.

## Target 3 — `test/retrieval.test.ts:452` (violates a written rule in this repository)

```js
console.log(`[D-24 MEASURED] rankSections linearity: small(4000-section) ${smallMs.toFixed(1)} ms, large(16000-section) ${largeMs.toFixed(1)} ms, ratio ${(largeMs / smallMs).toFixed(2)}`);   // :450

expect(largeMs / smallMs).toBeLessThan(10);  // :452   <-- the violation
```

**`CONTRIBUTING.md:75-77`:**

> *"**No assertion may compare two wall-clock measurements.** A ratio between two timed runs is the
> most flake-prone shape there is, and it has bitten this repository. Print a `[MEASURED]` line and
> assert an **absolute** ceiling instead — the number is the record, the threshold is not."*

`:452` is that exact shape. **`:451` already asserts the absolute ceiling and `:450` already prints
the ratio**, so the rule's prescribed replacement is already in place, one and two lines above.
**Delete `:452`.** The ratio survives as a printed number, which is what the rule asks for.

**Do not raise the `< 10` to make it safer.** The long comment above `:451` is an honest record of
two rounds of margin analysis — and it is also the "widen the threshold" path, reached twice. Keep
the comment; it explains why `:451`'s `< 10_000` is what it is. Trim only the part that justifies the
ratio, and say in the commit that it went for the `CONTRIBUTING.md:75` reason.
