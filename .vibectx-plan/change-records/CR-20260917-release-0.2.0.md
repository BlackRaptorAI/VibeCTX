# Change Record — CR-20260917-release-0.2.0

Per the lean process (D-70): one Change Record per release, not one per item. Individual
0.2.0 items each merged through their own PR, reviewed by `code-reviewer` (and
`security-architect` where the change touched URL/host policy, fetching, redirects, config
URL handling, or the on-disk cache/search index) — see each PR for that evidence. This record
is the release-level summary: what 0.2.0 actually is, what was verified against real data
before shipping, and the risks accepted rather than fixed.

## 1. Change summary

0.2.0 is the GA release covering the 2026-09-08 audit remediation batch (the `PAR-7xx` items
under the 0.2.0 milestone) plus A11 (version-matched documentation, PAR-724) and A16 (the
package-existence signal, PAR-725). `package.json` is bumped to `0.2.0` in this same PR, built
on `main` @ `c6a7b2c`; this record still precedes the tag, which Tom cuts after reviewing and
signing §7 below.

**What 0.2.0 promises, and doesn't:** version-matched documentation with a stated, non-silent
fallback when no pinned-version document exists (D-50, A11); the package-existence signal
(A16); provenance stamping on every response (A17); honest gap statements when nothing is
cached or nothing matches (A18); a redirect-aware primary document resolves its own relative
links and host policy against the host it was actually served from, not the pre-redirect
candidate (PAR-776, D-74); PEP 503 name-twin handling in the registry (PAR-777, D-78); the
Node engine floor now states the true intersection of `vite`'s and `vitest`'s own declared
ranges, enforced by a dedicated test rather than hand-maintained, and a CI matrix that runs
one version per declared band (PAR-778, PAR-779, PAR-829); the two moderate `vitest`-chain
advisories present at the earlier release-verification pass are resolved, not accepted
(PAR-830). **0.2.0 makes no retrieval-quality claim** — see §5.

## 5. Deviations & risk acceptance

> **Upgrading? Read this before concluding the release is broken.** An existing install will
> **not** see the clerk fix or the content-negotiation fixes below until the affected cache
> entry's TTL expires. Cache entries are keyed per-URL, and `getLibraryDoc` (`src/fetcher.ts`)
> reads cache-first, walking a library's candidate URLs in order and returning the first fresh
> hit before ever reaching the network — a fresh cached copy of the OLD (broken) result is
> served exactly as confidently as a fresh copy of the new one. **`vibectx warm --force` does
> NOT clear this** — it only bypasses a recent resolution-*failure* memo, never the document
> cache itself (verified: run against a deliberately poisoned cache, no change). What does
> work: deleting the affected library's cache directory, waiting out the TTL (168h default), or
> the MCP `refresh` tool (`src/refresh.ts`, which calls `getLibraryDoc` with
> `forceRefresh: true`, skipping the cache-first loop entirely). Someone who upgrades, runs
> `doctor`, and still sees `clerk` unhealthy has not found a broken 0.2.0 — they have found
> this gap. Tracked as **PAR-836** (no milestone assigned yet; the general defect will recur on
> any future curated-URL reorder, not just this one).
