**What changed and why (2–5 sentences):**
Agents often don't know which library owns a concept — "how do I stream a response to the client" could be Next.js, the Vercel AI SDK or Hono — so until now they had to guess a library name before they could ask anything. `search(query, maxTokens?, libraries?)` searches every cached library at once with the PAR-658 BM25 ranker and returns the best sections grouped by library, each with its heading path and source URL, under one shared token budget. It is cache-only by construction: no fetch, no resolution, no network on that path ever. A small on-disk inverted index (`<cacheRoot>/index.json`) is maintained incrementally so a search doesn't re-tokenize every cached document, and the response says how many of the configured libraries were actually searched, suggesting `warm` when the answer is "not all of them".

**Blast radius if wrong (prod deploys on merge — be honest):**
The index is the risk. If it were trusted, a corrupt, stale or planted `index.json` would decide what the model is told — so it is treated as a derived cache with no authority: it stores **no document text at all**, every posting is verified against a content hash of the cached document before use, and every rendered body is re-read and re-split from the cache itself (D-33). A stale-tokenizer index is the subtler version of the same failure and is now refused by a `RETRIEVAL_VERSION` on the envelope (D-38) — without it, a tokenizer change silently produced *wrong answers* while the hash still matched, which the schema gate demonstrated. The other failure mode is resource, not correctness: the first round could write an index larger than its own reader would accept (74.7 MB), poisoning itself into a 21.5-second-per-search loop, and could return 9.9× to 322× the caller's `maxTokens`. Both are fixed and pinned. Warm search costs ~820–919 ms at a 30-document / 146 MB cache versus 44–51 ms at 12 documents / 5.63 MB — both stated in the README rather than averaged away, the larger one reproducible via the committed probe.

**Behaviour changes worth knowing (release notes):**
1. **New MCP tool `search(query, maxTokens?, libraries?)`** and **CLI `vibectx search <query> [--library <name>]… [--json]`** (exit 0 hits / 1 no hits / 2 usage, matching the `doctor`/`warm` precedent). Results are grouped by library, libraries ordered by their best section, sections by score then document order, each group carrying its `Source:` line and a stale marker. The response ends with how many of the configured libraries were searched and, when not all are cached, the `warm` suggestion.
2. **Cache-only and offline (D-35).** `search` never fetches and never resolves — asserted with a fetch spy on every path including lazy indexing and the CLI. `libraries?` filters by name or alias through `resolveLibrary`; an unknown name is reported in the response, not an error.
3. **The index has no authority (D-33).** `<cacheRoot>/index.json` (schemaVersion 1, atomic, validated on read; a newer schemaVersion is never overwritten) stores per-section token counts and posting lists only — never text. A posting whose content hash doesn't match the cached document is ignored and rebuilt. Bodies always come from the cache. A missing or unreadable index degrades to on-the-fly indexing; a failed write is a note, never a failed search.
4. **The index is keyed to the code that built it (D-38).** `RETRIEVAL_VERSION` (in `src/tokenize.ts`) is stamped into the envelope and must be bumped when the tokenizer, the stemmer, `splitSections` or the BM25 field weights change; `readIndex` refuses a mismatched file whole. Bump reminders sit at all five governing sites.
5. **The budget is real (D-39), and the answer survives it (D-43).** Bodies, headings and paths are attached before selection, so `maxTokens` bounds the text actually returned — the rendered response and the summed `--json` bodies both. Selection is round-robin across libraries. At **any** budget the response carries the best-scoring library's name, its `Source:` line, and at least one section of its text; when the budget cannot hold both that and the accounting, **the accounting is what gives way** (other libraries drop, then the section body is clipped, then the footer shortens, then the footer goes — never the section). An irreducible minimum that exceeds the budget is announced in the response. The `n shown` count reports libraries actually emitted, never merely selected.
6. **The index cannot poison itself (D-40/D-42).** `writeIndex` sheds the largest entries until the file is under the size `readIndex` accepts, and names what it shed in the response; a shed library is remembered for the process (keyed by document hash, so a refreshed or shrunken document is retried) and is still searched by direct tokenization and still named on every call.
7. **Inputs are bounded (D-41).** `query` is capped at 1000 characters at the MCP schema, the CLI (clip reported on stderr *and* in the `--json` notes) and `runSearch`. A 200,000-term query previously exhausted a 2 GB heap and killed the server; it now returns in ~1 ms.
8. **Index maintenance (D-34).** Indexing happens at `resolvePackage`/`getLibraryDoc` — the single writer every primary-document path reaches (`get_docs`, `warm`, autowarm, `refresh`, resolution) — with one read and one merge-write per run (`openIndexSession`). Followed pages are never indexed. `refresh` invalidates and rebuilds; a failed refresh leaves the entry invalidated rather than stale.
